## Checks that survive optimization and acquire the actual lock

Every new executable entry rejects optimized Python with a real
conditional before importing repository infrastructure. The preferred
entry rejects optimization environment settings, removes them from the
child environment and execs the same interpreter with `-E -B`. Thus the
frozen assertion-based proof and resource checks remain enabled along
the new route. No scientific source was rewritten to change its expected
certificate or source bindings.

Direct checks default to the outer shared lock. Seven exemptions are
exact public source/argument tuples, not filenames. In particular the
self-hub source's internal `--worker` branch receives the outer lock;
its public `--verify` branch owns the inner lock. A duplicate lock for a
known self-locking public tuple is rejected. The catalogue tuples and
the exemption map were compared by the actual infrastructure tests.

Lean compilation and auditing are separate named operations. Both use
the unchanged outer bounded research runner without `--parent-lock`,
because the inner Lean operation owns that same lock. The actual-axiom
helper requires matching capped target compilation and valid dependency
objects under the lock and never compiles a missing target as a fallback.
Whole-project root targets are rejected by the public entry.

## Resource and process cleanup review

Actual checks and builds remain inside the original bounded runners.
Admission remains 40 GiB disk and 6 GiB available RAM, with 8/3 GiB abort
floors. Scientific work retains the 59-second, 1 GiB process-tree RSS
monitor and one thread. Lean retains its 2048 MiB and one-thread options
inside that stronger outer monitor. TeX uses the existing bounded builders.
The added process bridge is an ownership/cleanup layer, not a replacement
for any resource admission or monitor.

Root checked the Darwin process metadata layout, live identities and the
Linux field indexing used by the tracker. The bridge verifies process
monitoring before any child and holds its direct child behind a pipe
until that birth is tracked and the bridge's own owner is still valid.
A denied monitoring API fails closed. The bridge accepts only the current
Python executable and the named existing bounded runners/builders.

The tracker acquires descendants through a presently verified owned
parent or a still-owned process group, keeps already observed births
after reparenting, and never transfers ownership to a reused numeric PID.
Its group leader checks, exclusion of the coordinator's own group, and
immediate birth/group revalidation precede every signal. Inner compiler
groups are signalled before the outer monitors. Cleanup resamples,
escalates from TERM to KILL for verified owned groups, and fails if verified
owned live processes remain. A successful leader with surviving children
is cleaned and reported as a failure rather than a proof PASS.

This fixes the concrete nested-session cleanup race in the earlier route.
Polling cannot observe an arbitrary adversarial fork/reparent race, and
Darwin has no atomic pidfd signal handle. The code and review disclose
those limits; this clearance claims the implemented ownership checks and
tested lifecycle, not an atomic operating-system guarantee.

publishes its operational audit ledger. It requires exactly one result
for each requested declaration. Qualified requests match exactly; local

duplicate or extra results fail. Malformed result headers, empty comma
items, duplicate axioms, unsupported identifiers, `sorryAx` and any axiom
